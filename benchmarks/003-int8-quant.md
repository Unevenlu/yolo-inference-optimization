# 003 - INT8 量化（NNCF）：大小 / 延迟 / 精度的三者权衡

**日期**: 2026-10-13

## 目的

用 OpenVINO NNCF 对 yolo26n 做 INT8 训练后量化（PTQ），首次引入精度指标（mAP），回答量化最核心的一个问题：**用多少精度损失，换多少体积和速度收益**。

## 方法

- 量化方式：`export(format="openvino", int8=True)`，NNCF 训练后量化
- 校准数据：coco128（128 张 COCO 子集图片，统计收集 13s + Fast Bias Correction 2s，总导出耗时仅 27s）
- 精度验证：同一 coco128 上跑 `model.val()`，对比 FP32 / FP16 / INT8 三者的 mAP50-95 与 mAP50

## 结果

| 引擎 | 大小(MB) | 推理(ms) | e2e(ms) | mAP50-95 | mAP50 |
|------|----------|----------|---------|----------|-------|
| PyTorch (FP32) | 5.29 | 42.81 | 54.18 | 0.4859 | 0.6475 |
| OpenVINO (FP16) | 5.12 | 41.49 | 50.92 | 0.4788 | 0.6432 |
| OpenVINO (INT8) | **3.21** | **33.02** | **41.73** | 0.4685 | 0.6394 |

## 观察

- **INT8 的收益**：相对 FP32，体积 -39%（5.29→3.21MB），推理 -23%（42.8→33.0ms），e2e -23%。
- **精度代价很小**：mAP50-95 仅掉 1.7 个点（0.486→0.469），mAP50 掉 0.8 个点。对大多数端侧场景这是完全可接受的交易。
- **FP16 基本无损**：mAP 掉 0.7 个点以内，结合实验 002 的结论，FP16 是"零风险打底"，INT8 是"小代价换大收益"。
- **NNCF 为什么能保住精度**：日志显示 NNCF 自动跳过了检测头附近的 28 个敏感算子（Reshape/Concat/Subtract/Divide/Sigmoid 等不插入激活量化器），只对算力密集的卷积做量化，并有 Fast Bias Correction 校正——敏感层高精度 + 逐层校正是现代 PTQ 的标准做法。
- **累积成果**：从 PyTorch FP32 基线（5.29MB / e2e ~54ms）到 OpenVINO INT8（3.21MB / e2e ~42ms），零训练成本。

## 注意

- 本轮三个引擎的绝对耗时都高于实验 002（系统负载差异），但同场相对关系可信：INT8 比同场 FP32 快 23%。
- coco128 只有 128 张图，mAP 绝对值不代表 COCO 官方水平，但**同一数据集上的相对比较**用于判断量化损失是足够的。正式结论应在完整 COCO val2017 上复核。
- INT8 提速幅度（23%）小于体积压缩幅度，因为 i7-1260P 的 AVX2 对 INT8 的加速有限（VNNI 指令集在更新的 CPU / NPU 上收益会更大）——这解释了为什么端侧 NPU 普遍以 INT8 为主力精度。
